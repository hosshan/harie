# ADR-0004: 画像保存形式: XMP 記述子 + JUMBF ペイロード埋め込み

- ステータス: 提案中
- 日付: 2026-10-07
- 決定者: Shun（承認待ち）
- 関連: [技術調査: 画像保存方式](../02-research/image-storage.md) / [ファイル形式仕様](../03-design/anoi-format-spec.md) / FR-FILE-01〜07 / [ADR-0007](./0007-pii-masking.md)

## 背景

要求 R1（通常の画像として表示）と R2（保存後も注釈を変更可能）を、1 ファイルで同時に満たす必要がある。他人が作ったファイルも編集できること（課題 P4）から、サイドカーや独自形式への分離は避けたい。再編集には注釈 JSON に加えて「注釈を焼き込む前のベース画像」も必要で、ファイルサイズは通常の約 2 倍になる。

## 選択肢

### A. XMP（APP1）にすべて格納（Extended XMP）

- 長所: 最も標準的。多くのツールが保持する。
- 短所: バイナリを Base64 にするため 33% 膨張。Extended XMP の分割規則が独特。

### B. XMP 記述子（APP1）+ JUMBF ペイロード（APP11）

- 長所: バイナリをそのまま格納できる。分割規則が ISO で標準化。C2PA と同じ入れ物で、C2PA 対応の普及に伴い保持するツールが増えている。XMP 記述子で標準ツールからも Anoi ファイルと識別できる。
- 短所: 実装がやや手間（PoC で約 150 行）。C2PA マニフェストと共存させる場合の配慮が要る。

### C. 独自 APPn / EOI 後への追記

- 長所: 実装が最も簡単。
- 短所: 非標準。他ツールでの保持が期待できない。識別子衝突のリスク。

### D. サイドカーファイル / 独自コンテナ

- 長所: 実装が簡単。画像サイズが増えない。
- 短所: 1 ファイルで完結しない。書き出した画像から再編集できない。要求を満たさない。

## 決定

**B を採用する。** PNG も同じ JUMBF ペイロードを独自チャンク `anOi` に、記述子を `iTXt` の XMP に格納する。

PoC（`docs/02-research/poc/anoi-jpeg-poc.mjs`）で、Chromium・Pillow・ImageMagick が通常の JPEG として表示でき、ベース画像がバイト単位で復元できることを確認した。

あわせて以下を決める。

- ベース画像は元のバイト列のまま格納し、再エンコードしない（劣化させない）。
- XMP 記述子に `payloadSha256` と `renderSha256` を持ち、外部ツールでの再エンコード・一部欠損を検出する。
- EXIF は既定で書かず、取り込み時にも除去する。

## 結果（影響）

- 良くなること: 1 ファイルで表示と再編集が両立する。他人に渡しても編集できる。
- 受け入れるコスト:
  - ファイルサイズが約 2 倍になる（NFR-PERF-03 で許容）。
  - 再エンコードするサービス（SNS、チャット等）を通すと埋め込みデータは消える。原本は Git・共有ドライブに置く運用をガイドに書く。
- 後でやること:
  - クラウドに docId で控えを置き、消えたデータを復元する（FR-FILE-10）。
  - C2PA マニフェスト（「PII 加工済み」等の来歴）を同じファイルに付けられるか検証する。
