# ADR-0005: 描画パイプライン: 注釈 → SVG → resvg（WASM）

- ステータス: 提案中
- 日付: 2026-10-07
- 決定者: Shun（承認待ち）
- 関連: NFR-PLAT-05 / FR-MCP-03 / [アーキテクチャ](../03-design/architecture.md) / [ADR-0002](./0002-app-platform.md)

## 背景

同じ注釈ドキュメントから、Web・拡張・デスクトップ・MCP（Node, UI なし）のどこで保存しても同じピクセルが出る必要がある。ブラウザの Canvas 2D は環境ごとにアンチエイリアス・フォント描画が異なり、Node には標準の Canvas がない。

## 選択肢

### A. 注釈 → SVG 文字列 → resvg（WASM）でラスタライズ → ベース画像と合成 → エンコード

- 長所: resvg は描画結果が環境に依存しない（フォントも明示的に渡す）。WASM 版はブラウザ・Node・拡張で同じバイナリが動く。SVG はエディタの表示にもそのまま使える。
- 短所: WASM のサイズ（数 MB）。日本語フォントの同梱が必要（サブセット化してもサイズが大きい）。

### B. Canvas 系ライブラリ（Konva / Fabric）で描画し、Node では node-canvas / skia-canvas

- 長所: エディタのインタラクション実装が楽。
- 短所: ブラウザと Node で描画エンジンが異なり、ピクセルが一致しない。node-canvas はネイティブ依存で配布が面倒。

### C. ヘッドレスブラウザで描画（MCP 側）

- 長所: エディタと同じ描画。
- 短所: MCP サーバーが Chromium を必要とし、重い。

## 決定

**A を採用する。**

- `packages/render` に「注釈ドキュメント → SVG」の純粋関数を置き、エディタの表示もこの SVG を使う（表示と保存の見た目を一致させる）。
- ラスタライズは resvg-wasm、合成とエンコードは WASM のコーデック（jSquash 等の mozjpeg / oxipng）を第一候補とする。実装時に性能（NFR-PERF-01）を計測して確定する。
- フォントは Noto Sans JP 等のオープンライセンスのフォントを同梱し、ドキュメントにはフォント ID のみ記録する。
- エディタの操作（選択・移動・リサイズのハンドル）は SVG 上に React で実装する。キャンバスライブラリは使わない。

## 結果（影響）

- 良くなること: どこで保存しても同じ見た目。MCP から編集しても見た目が変わらない。表示用と保存用の描画が 1 本。
- 受け入れるコスト: WASM とフォントの初回ロード（数 MB）。PWA のキャッシュで緩和する。
- 再評価の条件: 保存が 2 秒を超える、またはエディタの操作が重い場合は、表示のみブラウザネイティブの SVG 描画にし、保存時だけ resvg を使う構成（現行案の範囲内）に寄せる。
