# MCP の効果検証: コンテキスト効率と品質の安定性（FR-MCP-01〜04）

ステータス: 確定（計測 1 回目） / 最終更新: 2026-10-14

Harie の MCP（`@harie/mcp`）を使うと、使わずに画像へ直接描き込む場合に比べて、AI エージェントのコンテキスト効率が良く、出来上がる利用ガイド画像の品質が安定するのかを確かめた。

## 結論

- **新しく作る（create）ときは、MCP のほうがコンテキストを多く使う。** 入力トークンの合計は MCP 0.2.0 が約 10.6 万、MCP なしが約 4.8 万で約 2.2 倍、コストも約 2.3 倍（0.116 / 0.050 USD）。終了時のコンテキストも約 2.1 万 / 1.2 万。
  - 理由は 2 つ。(1) ツール定義が毎ターン約 3.3k トークン乗る（最初の呼び出しの入力が MCP 8.9k / なし 5.6k）。(2) `harie_open`・`harie_mask`・`harie_edit` が毎回描画後の画像を返すため、画像がコンテキストに平均 5.1 枚入る（MCP なしは確認したいときだけ Read するので 2.5 枚）。
- **既存の画像を直す（revise。別のセッションで）ときは、MCP のほうが効率が良く、ばらつきも小さい。** 入力トークン合計は 4.5 万 ± 0.5 万 / 7.6 万 ± 2.4 万、ツール呼び出しは 3.1 回 / 9.4 回、出力トークンは 0.6k / 2.9k、時間は 11 秒 / 30 秒。MCP は `harie_list → harie_open → harie_edit` のほぼ決まった 3 手で終わる。MCP なしは、前回の画像の画素を調べ、拡大して確かめ、背景色で塗りつぶして描き直す手順を毎回組み立てるため、手数とトークンが揺れる（最大 13.2 万）。
- 作成 1 回 + 修正 1 回の合計では、まだ MCP なしのほうが少ない（約 15.1 万 / 12.3 万）。修正 1 回あたり約 3 万の差が付くので、**修正を 2 回以上重ねる画像なら MCP のほうが少なくなる**計算。
- **品質は、このお題ではどちらも安定していて差は小さい。** 全 48 試行で、必須の 3 か所を囲み、順番を正しく付け、個人情報を隠せた。修正の指示もすべて反映され、他の注釈と加工が保たれた。総合点は create で MCP 0.2.0 が 3.8 ± 0.4、MCP なしが 4.0 ± 0.0 で、MCP のほうがやや低い。
  - MCP の減点の主因は **吹き出しの日本語の改行**（「選びま／す」のように語の途中で折り返す）と、**番号バッジが操作対象に重なる**こと。文字の読みやすさは 3.8 / 4.8。どちらも `packages/render` と注釈の配置の問題で、エージェントの判断の問題ではない。
- **PR #31（0.3.0、補足の手引きを instructions で渡す）では説明文が良くなった**（説明文 4.4 → 5.0、修正後の総合 4.3 → 4.8）。一方で、instructions の分だけ毎ターンのトークンが少し増え（最初の入力 8.9k → 9.35k）、枠の合い方は 4.9 → 4.3 に下がった。
- 数字に出ない差として、MCP の出力は Harie ファイルなので注釈が構造のまま残り、別の人・別のセッションでも同じ手順で直せる。MCP なしの出力は普通の画像で、直すたびに描き直しになる。

## 改善の候補

効果の大きい順。どれも提案で、実装の前に別途判断する。

1. **ツール結果の画像を減らす。** create のトークン差の大半はここにある。例: `harie_edit` / `harie_mask` に画像を返さない（または縮小して返す）指定を設ける、`harie_create` が画像を返して直後の `harie_open` を不要にする。
2. **吹き出しの日本語の折り返しを直す**（禁則処理や、語の途中で切らない折り返し）。MCP の品質の減点の主因で、Web エディタの出力にも同じ影響があるはず。
3. **番号バッジと吹き出しの自動配置**で操作対象に重ならないようにする。
4. `harie_edit` の ops で、数値を `"w":054` のように先頭 0 付きで書いて JSON として壊れる呼び出しが、0.2.0 の create 8 回中 4 回、0.3.0 で 8 回中 2 回あった（1 ターン無駄になる）。座標の差し引き計算で起きている可能性があるが、原因は確かめていない。

## 計測条件

- お題の画像: 架空のタスク管理 SaaS の通知設定画面（1280×720、`apps/mcp/eval/fixtures/`）。ダミーの氏名とメールアドレス（example.com）が 2 か所に写っている。
- create のお題: 「Slack に通知を送るように設定する手順」のガイド画像を作る。操作箇所を枠で囲み、順番と説明文を付け、個人情報を読めないように加工する。
- revise のお題: create の結果を新しいセッションで開き、1 つの説明文を指定の文言に変え、右上の「?」に補足を加え、他はそのまま残す。
- 条件（どれも Claude Code の `claude -p`、モデル Claude Sonnet 5.5、各 8 回）:
  - MCP 0.2.0: npm の `@harie/mcp@0.2.0`。使えるツールは harie の 6 つと Read・Glob。
  - MCP 0.3.0: PR #31 のブランチをビルドしたもの。ツールは同上。
  - MCP なし: Bash・Read・Write・Edit・Glob。Python（Pillow）と日本語フォント（IPA ゴシックなど）が入った環境。
- 子のセッションには親のメモリ・CLAUDE.md・設定を渡さない。作業ディレクトリはリポジトリの外。
- 品質は Claude Opus 5.5 が画像を見て採点した（ルーブリックは `apps/mcp/eval/judge.mjs`）。正解の矩形を渡している。
- 指標の意味: 「入力トークン合計」は API 呼び出しごとの入力（キャッシュ読み込みを含む）の合計、「終了時のコンテキスト」は最後の呼び出しの入力。

## 限界

- 画面 1 枚、お題 2 つ、モデル 1 つ、各 8 回の結果。もっと複雑な画面・長い手順・大きな画像（Retina の 2 倍など）では、画像を返すコストも描き直しの難しさも大きくなる。
- 採点は LLM で、48 件中 2 件はダミー値への置き換えを「個人情報が残っている」と誤って判定したため、その 2 件だけ採点し直した。点数は目安で、0.2 程度の差は誤差の範囲と見る。
- MCP なしの条件では、エージェントが作ったスクリプトは一時ディレクトリに置かれて次のセッションに残らなかった。スクリプトを残す運用なら、修正のコストはもっと下がる。
- MCP の条件に Bash を与えていない。実際の利用ではどちらも使えることが多い。

## 再測定の手順

`apps/mcp/eval/README.md` を参照。MCP サーバーの起動コマンドを `--mcp` で差し替えれば、同じお題で新しい版を測れる。
