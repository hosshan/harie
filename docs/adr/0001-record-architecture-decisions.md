# ADR-0001: ADR で設計判断を記録する

- ステータス: 承認
- 日付: 2026-10-07
- 決定者: Shun（PdM / エンジニア）
- 関連: [ADR 運用ルール](./README.md) / [ADR-0008](./0008-ai-development-harness.md)

## 背景

Harie は少人数 + AI エージェント（Claude Code 等）で開発する。AI エージェントは会話をまたいで記憶を持たないため、「なぜこの技術を選んだか」「何を検討して捨てたか」がリポジトリに残っていないと、同じ検討を繰り返したり、過去の判断と矛盾する実装をしたりする。人間のメンバーが増えたときも同じ問題が起きる。

## 選択肢

### A. ADR（1 判断 1 ファイル、Markdown、リポジトリ内）

- 長所: コードと同じ場所・同じレビューで管理できる。AI がファイルとして読める。履歴が Git に残る。
- 短所: 書く手間がかかる。

### B. 設計書に追記していく

- 長所: 1 か所にまとまる。
- 短所: 判断の時点と理由が上書きで消えやすい。「今の設計」と「経緯」が混ざる。

### C. Issue / PR / チャットの議論に任せる

- 長所: 追加の手間がない。
- 短所: 散らばって見つからない。AI エージェントから参照しにくい。

## 決定

A を採用する。設計書（`docs/03-design/`）は「今の形」を、ADR は「判断と理由」を持つ、と役割を分ける。形式は MADR を簡略化した日本語テンプレート（[`template.md`](./template.md)）とする。

## 結果（影響）

- 良くなること: 判断の経緯が残り、AI エージェントが参照できる。レビューで判断そのものを議論できる。
- 受け入れるコスト: 重要な判断ごとに 1 ファイル書く。
- 再評価の条件: ADR が形骸化した（書かれない・読まれない）と感じたら、運用ルールを見直す。
