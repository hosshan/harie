# 技術調査: 画像保存方式（通常画像として表示でき、保存後も再編集できる形式）

- ステータス: 調査完了（決定は [ADR-0004](../adr/0004-image-container-format.md)）
- 調査日: 2026-10-07
- PoC: [`poc/anoi-jpeg-poc.mjs`](./poc/anoi-jpeg-poc.mjs)

## 1. 問い

次を同時に満たす保存方式は何か。

1. 一般的なビューア・ブラウザ・CMS で**普通の JPEG / PNG として表示**される（FR-FILE-01, 02）
2. Anoi で開くと**注釈を個別に再編集**できる（FR-FILE-03）
3. 何度保存しても**下地の画質が劣化しない**（FR-FILE-04）
4. 1 ファイルで完結し、他人に渡しても編集できる（P4, NFR-DATA-04）

## 2. 何を保存する必要があるか

再編集には「注釈の構造データ」だけでは足りない。JPEG のピクセルには注釈が焼き込まれているため、**注釈を焼き込む前の下地（ベース画像）**も必要になる。

| 保存物 | 役割 | サイズ感 |
|---|---|---|
| レンダリング画像 | 外部ツールで表示されるピクセル（注釈焼き込み済み） | 画像本体 |
| 注釈ドキュメント（JSON） | 枠・テキスト等の構造データ | 数 KB〜数十 KB |
| ベース画像 | 再編集時の下地。PII 加工済み | 画像本体とほぼ同じ |

→ **ファイルサイズは通常の約 2 倍**になる。これは方式によらない本質的なコスト（NFR-PERF-03 で許容値を定義）。

> 注意（重要）: ベース画像には**マスク前の個人情報を絶対に残さない**。マスクを「注釈」として可逆に持つと、埋め込まれたベース画像から元の情報が復元できてしまう。PII 加工はベース画像に不可逆に適用する（[ADR-0007](../adr/0007-pii-masking.md)）。

## 3. 埋め込み先の候補

### 3.1 JPEG の格納場所

JPEG は `SOI` の後に `APPn`（n=0〜15）セグメントを任意個置ける。デコーダは知らない APPn を読み飛ばすので、表示には影響しない。1 セグメントの上限は約 64KB。

| 候補 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| A. XMP（APP1） | Adobe の XML メタデータ。64KB 超は Extended XMP で分割 | 標準。exiftool・Adobe 製品・多くのツールが保持 | XML なのでバイナリ（ベース画像）は Base64 で 33% 膨張。Extended XMP の分割規則が独特 |
| B. JUMBF（APP11） | ISO/IEC 19566-5 の箱形式。C2PA（Content Credentials）と同じ入れ物 | バイナリをそのまま格納。分割規則が標準化。C2PA 普及により保持するツール・サービスが増えている | 実装がやや手間（ただし PoC で 150 行程度） |
| C. 独自 APPn | 任意の APPn に独自署名で格納 | 実装が最も簡単 | 識別子の衝突リスク。他ツールに保持される期待が持てない |
| D. EOI 後への追記 | 画像データ末尾の後ろに付ける（Google Motion Photo 方式） | どんなサイズでも 1 ブロック | 規格外。トリミングするツールがある。ストリーミング読み込みで末尾まで読む必要 |
| E. EXIF（APP1） | EXIF の MakerNote / UserComment | — | 64KB 制限が厳しく、構造化データ向きでない。不採用 |
| F. サイドカー | `example.jpg` + `example.anoi.json` | 実装が最も簡単。画像サイズが増えない | 2 ファイルを一緒に扱う必要があり、要求「1 ファイルで他人も編集」（P4）を満たさない |
| G. 独自コンテナ | `.anoi` 形式（zip 等）＋書き出し JPEG | 自由度最大 | 書き出した JPEG からは再編集できない。要求 R1/R2 を同時に満たさない |

### 3.2 PNG の格納場所

PNG はチャンク構造で、サイズ上限は実質なし。

- XMP: `iTXt` チャンク（キーワード `XML:com.adobe.xmp`）
- バイナリ: 独自のアンシラリチャンク `anOi`（小文字始まり=補助、2 文字目小文字=私用、4 文字目小文字=コピー安全）。C2PA は `caBX` に JUMBF を入れる。

### 3.3 WebP（Later）

RIFF チャンク（`XMP ` と独自チャンク）で同様に実現できる。MVP 対象外。

## 4. メタデータの「生存性」

埋め込みデータは、**外部ツールで再エンコードされると基本的に失われる**。これはどの方式でも同じで、方式選定の決め手にはならないが、検出と復元の設計が必要。

PoC での確認結果（ImageMagick 6 / Pillow 12.3 / Chromium 141 系、2026-10-07）:

| 操作 | XMP 記述子 | 注釈 JSON（APP11, 1 セグメント） | ベース画像（APP11, 7 セグメント） |
|---|---|---|---|
| ファイルコピー | 残る | 残る | 残る |
| Chromium で表示 | 正常表示（1280×800） | — | — |
| Pillow で開いて再保存 | **消える** | **消える** | **消える** |
| ImageMagick でリサイズ／再圧縮 | 残る | 残る | **消える**（先頭の 1 セグメントだけ残り、長さが合わなくなる） |
| ImageMagick `-strip` | 消える | 消える | 消える |

一般に知られている傾向（要個別検証）:

- SNS・チャットツール（Slack、X など）は画像を再エンコードし、メタデータを削除することが多い。
- ヘルプ CMS（Zendesk、Intercom、Notion 等）は元ファイルをそのまま配信することが多いが、サムネイル生成時に削除される場合がある。
- Google Drive・Dropbox・Git はバイト列を保持する。

→ **「Anoi ファイルの原本」は Git・共有ドライブなどバイトを保持する場所に置き、CMS には書き出しコピーを上げる**運用を推奨としてガイドに書く。

### 4.1 不整合の検出（FR-FILE-05）

ImageMagick の例のように「一部だけ残る」と、注釈 JSON はあるのにピクセルがリサイズ済みという不整合が起きる。これを検出するため、XMP 記述子に次を記録する。

- `payloadSha256`: 埋め込みペイロード全体のハッシュ（欠損・改ざん検出）
- `renderSha256`: レンダリング画像の圧縮データ（`SOS` 以降）のハッシュ（外部での再エンコード検出）

読み込み時にどちらかが一致しなければ「外部で編集された可能性」として扱い、ユーザーに選ばせる（埋め込みから復元 / 現在のピクセルを新しいベースにする）。

### 4.2 将来の復元手段（FR-FILE-10, Later）

docId をキーにクラウドへ控えを保存すれば、メタデータが消えたファイルもピクセルの知覚ハッシュ等で照合して復元できる。C2PA の「soft binding」と同じ考え方。

## 5. PoC

[`poc/anoi-jpeg-poc.mjs`](./poc/anoi-jpeg-poc.mjs)（依存なし、Node 22）で、B 案（XMP 記述子 + APP11 JUMBF）を実装して確認した。

```sh
node docs/02-research/poc/anoi-jpeg-poc.mjs write rendered.jpg base.jpg out.anoi.jpg
node docs/02-research/poc/anoi-jpeg-poc.mjs read out.anoi.jpg extracted-base.jpg
```

結果:

- 1280×800 の画像で、rendered 355KB + base 349KB → 出力 706KB（APP11 7 セグメント）。
- 出力ファイルのピクセルは rendered と完全一致（ImageMagick `compare -metric AE` で差分 0）。
- 抽出したベース画像は入力とバイト単位で一致（`cmp` 一致）。再エンコードしないので劣化しない（FR-FILE-04）。
- Chromium・Pillow・ImageMagick いずれも通常の JPEG として正常にデコード。

## 6. 結論（推奨）

**JPEG: XMP 記述子（APP1）+ JUMBF ペイロード（APP11）。PNG: XMP（iTXt）+ 同じ JUMBF ペイロード（独自チャンク）。**

- XMP には小さな記述子（docId・バージョン・ハッシュ）だけを置き、exiftool 等の標準ツールから「Anoi ファイルであること」が見える状態にする。
- 本体（注釈 JSON・ベース画像）は JUMBF に格納する。バイナリを膨張させず、分割規則が標準化されており、C2PA と同じ入れ物なので将来の来歴証明（「PII 加工済み」の証明など）にも接続しやすい。
- ベース画像は元のエンコード（JPEG/PNG のバイト列）をそのまま格納し、再エンコードしない。
- サイドカー・独自コンテナは要求（1 ファイル完結・通常画像）を満たさないため不採用。

仕様は [Anoi ファイル形式仕様](../03-design/anoi-format-spec.md) に定義する。

## 7. 残課題

- C2PA 署名付きファイルとの共存（C2PA マニフェストも APP11 を使う。Box Instance 番号の衝突回避が必要）。
- ベース画像を JPEG で持つか PNG で持つか（スクリーンショットは PNG の方が文字が綺麗だが大きい）。既定は「キャプチャ時の形式をそのまま」。
- 大きな画像（4K 以上）でのメモリ使用量と保存時間の計測（NFR-PERF-01）。
