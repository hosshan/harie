# ADR-0006: 保存ファイル名の規則

- ステータス: 承認
- 日付: 2026-10-07
- 決定者: Shun（2026-10-07 承認）
- 関連: 要求 R3 / FR-FILE-06 / [ADR-0004](./0004-image-container-format.md)

## 背景

要求時のファイル名イメージは `example.{anoi:サービス名}.jpeg`。`{anoi:サービス名}` は「**この部分には本プロダクトのサービス名が入る。現時点の仮名は `anoi`**」という意味で、正式名称が決まったら差し替える前提（2026-10-07、Shun に確認）。

意図は「ファイル名を見ただけで、このツールで作った再編集できる画像だとわかる」こと。

文字どおりの表記には問題がある。

- `:` は Windows のファイル名に使えない。
- `{}` は URL・シェル・一部の CMS で扱いにくい。

なお、Anoi ファイルかどうかの判定は**ファイル名ではなく埋め込みデータ**で行う（ADR-0004）。ファイル名は人間向けのヒントであり、名前を変えても再編集はできる。

## 選択肢

検討時は「サービス名」を利用者側の SaaS 名と誤解して A〜C を比較した。正しい解釈では、C がそのまま要求どおりの形になる。

### A. `<名前>.<利用者のサービス>.anoi.jpg`

- 短所: 要求の意図（プロダクト名マーカー）と異なる要素が増える。

### B. `<名前>.anoi-<利用者のサービス>.jpg`

- 短所: 同上。末尾が一定でない。

### C. `<名前>.<プロダクト名>.jpg`（現時点は `<名前>.anoi.jpg`）

- 長所: 要求どおり。短く、`*.anoi.*` で一括検索できる。

## 決定

**C を採用する。** 形式は `<名前>.<プロダクト名マーカー>.<拡張子>`、現時点では `notification-settings.anoi.jpg`。

- **マーカーは差し替え可能な定数として 1 か所（`packages/model` の定数）で定義する。** 正式名称が決まったらその値を変えるだけで、保存時のファイル名・ファイル関連付け・MCP の既定検索パターンが追従するようにする。
- 名称変更後も、旧マーカー（`anoi`）のファイル名は読み込み・検索の対象に含める（既存ファイルを改名させない）。
- 使用可能文字は `a-z 0-9 -`。日本語名や記号は保存時にスラッグ化する（英数字の入力を促し、なければ日時ベース）。
- 拡張子は `.jpg` / `.png`（`.jpeg` も読み込みは可）。
- 利用者側のサービス名はファイル名に入れない。必要ならフォルダ構成で分け、注釈ドキュメントの `meta.service` に記録する。

### ファイル形式内の識別子は名称変更の対象外

XMP 名前空間（`https://anoi.app/ns/1.0/`）、JUMBF ラベル（`anoi.document` 等）、PNG チャンク名（`anOi`）はファイル形式の識別子であり、プロダクト名が変わっても**変えない**。変えると既存ファイルとの互換が壊れるため。ブランド名とは独立した技術的な識別子として扱う（名前空間 URL のドメインは正式名称決定時に [形式仕様](../03-design/anoi-format-spec.md) v0.1 確定前なら見直してよい）。

## 結果（影響）

- 良くなること: OS・URL・Git で安全に扱える。名称変更が定数 1 つの変更で済む。
- 受け入れるコスト: 名称変更後はしばらく新旧 2 つのマーカーが混在する。
