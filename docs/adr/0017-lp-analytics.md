# ADR-0017: 紹介ページにだけ Google アナリティクスを入れ、アプリには入れない

- ステータス: 提案中（PR のマージで承認）
- 日付: 2026-11-13
- 決定者: Shun
- 関連: NFR-SEC-01, NFR-SEC-06, [アーキテクチャ 6. 横断的関心事（テレメトリ）](../03-design/architecture.md), apps/site

## 背景

harie.studio の紹介ページ（LP）がどれだけ読まれ、どこから来て、どれだけエディタを開いているかを知りたい（Shun、2026-11-13）。GitHub Pages のアクセス記録は開発者には見えないため、計測の仕組みがない。

一方で、プライバシーポリシー（Chrome ウェブストアの掲載からもリンクしている）、LP、`llms.txt` は「画像は端末の中で処理し、開発者は何も受け取らない。アクセス解析もない」と約束している。アーキテクチャ文書も「テレメトリは送らない。入れる場合は ADR を書く」としている。

## 選択肢

### A. 紹介ページだけに GA4 を入れる。EEA・英国・スイスは Cookie を使わない計測にする

- 長所: エディタ・拡張・デスクトップ・MCP の「解析なし」の約束はそのまま。LP の流入元とエディタを開いた数が分かる。同意バナーを作らずに、GDPR の Cookie 同意の問題を避けられる。
- 短所: EEA などの数字は Google のモデリングに頼るため粗い。紹介ページについてはポリシーの書き換えが要る。

### B. 紹介ページだけに GA4 を入れ、全地域で通常の（Cookie を使う）計測にする

- 長所: 実装が一番簡単で、数字が細かい。
- 短所: EEA の訪問者に対して、同意なしで解析用の Cookie を置くことになる。

### C. Web エディタ（/app/）にも GA4 を入れる

- 長所: 実際に使われている量（起動数、機能の利用）が分かる。
- 短所: 「アプリは解析なし」の約束を崩し、ポリシーとストアの説明を大きく書き換えることになる。オフラインで動く PWA に外部への通信が入る。

### D. GA ではなく Cookie を使わない解析（Cloudflare Web Analytics など）を使う

- 長所: 同意の問題がない。
- 短所: Shun が GA を求めている。GitHub Pages では Cloudflare のプロキシを前に置かないと使えず、DNS の構成が変わる。

## 決定

**A を採用する。**

- 対象は `apps/site` のページ（LP 各言語とプライバシーポリシー）だけ。`apps/site/scripts/build.mjs` が `dist/` に写したあとで `<head>` に差し込み、その後で Web エディタを `dist/app/` に写すので、エディタには入らない。
- 測定 ID は `apps/site/scripts/analytics.mjs` の `GA_MEASUREMENT_ID` に置く（秘密ではない）。空なら何も入れない。
- `harie.studio` で開いたときだけ読み込み、ローカルの確認やプレビューは数えない。
- 同意モード: EEA 30 か国・英国・スイスは `analytics_storage` を `denied`（Cookie を使わない計測）、それ以外は `granted`。広告のための項目（`ad_storage` など）は全地域で `denied`。Google シグナルと広告のパーソナライズは切る。
- 拡張計測の離脱クリックに入らない、エディタ（`/app/`）を開くリンクのクリックを `open_editor` イベントで数える。

## 結果（影響）

- 良くなること: LP の効果（流入元、言語ごとの読まれ方、エディタを開いた割合）が分かる。GA で Search Console の所有者確認もできる。
- 悪くなること・受け入れるコスト: 紹介ページから Google への通信が増える。プライバシーポリシー（日英）と `llms.txt` を「アプリには解析なし、紹介ページだけ GA」に書き換える。
- 後でやること / 再評価の条件: エディタの利用量を測りたくなったら、新しい ADR で C を検討する。同意バナーを出すことにしたら、EEA の `analytics_storage` を同意に合わせて `update` する。
