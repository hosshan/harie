# 描画・保存の性能計測（NFR-PERF-01）

ADR-0005（注釈 → SVG → resvg-wasm → エンコード）を `packages/render` で実装し、2560×1600 の保存時間を計測した。

## 結論

- 目標「2560×1600 の保存（レンダリング＋エンコード＋埋め込み）が 2 秒以内」は、計測環境では満たす。
- スクリーンショットに近い画像で約 1.0〜1.2 秒、情報量の多い最悪ケース（ノイズ状の合成画像）で約 1.8〜1.9 秒（初回のみ約 2.4 秒）。
- 最悪ケースでは余裕が小さい。M3 でブラウザ（Web Worker）上の実測を取り、2 秒を超えるなら下の「次の手」を検討する。ADR-0005 の再評価条件にはまだ当たらない。

## 計測条件

- 環境: クラウド開発コンテナ（Linux, Node 22, シングルスレッドの WASM）。ブラウザ未計測。
- 入力: 2560×1600 のベース画像（JPEG）、注釈 20 個（枠 10、日本語の吹き出し 10）。
- フォント: Noto Sans JP Regular / Bold（各約 5.7MB の TTF）。
- JPEG エンコード: mozjpeg（@jsquash/jpeg）、品質 90、`progressive: false`。
- 計測コード: `packages/render/src/renderer.test.ts` の NFR-PERF-01 テスト（結果は標準出力に出す）。

## 内訳

| 工程 | スクリーンショット相当 | 最悪ケース（ノイズ状） |
|---|---|---|
| SVG 生成（`buildSvg`） | 約 20ms | 約 20ms |
| Resvg の構築（フォント読み込み含む） | 約 10〜60ms | 約 10〜60ms |
| ラスタライズ（ベース画像のデコード含む） | 約 0.5〜0.7 秒 | 約 0.5〜0.7 秒 |
| JPEG エンコード | 約 0.3〜0.4 秒 | 約 1.1〜1.2 秒 |
| 埋め込み（`writeAnoi`、SHA-256 含む） | 約 50ms | 約 50〜80ms |

- ラスタライズの大半はベース画像のデコードで、注釈の数・日本語テキストの影響は小さい。
- エンコード時間は画像の情報量に比例する。UI のスクリーンショットは平坦な領域が多く速い。

## 分かったこと

- **ベース画像はキャンバスと同じ大きさで描く**。520×400 の画像を 2560×1600 に拡大して描くと、高品質な補間のためラスタライズが約 1.4 秒に増えた（`imageRendering: optimizeSpeed` で約 0.35 秒）。通常の保存ではベース画像とキャンバスは同じ大きさなので問題にならない。
- mozjpeg の `optimize_coding: false` や量子化テーブルの変更は、速度の改善が誤差程度でファイルが 1.6 倍に増えるため採用しない。
- `progressive: true`（既定）は遅くなるため切っている。

## 次の手（2 秒を超えた場合）

1. 保存処理を Web Worker で行い、UI を止めない（体感の改善。M3 で実施予定）。
2. フォントをサブセット化し、Resvg の構築と初回ロードを軽くする。
3. ブラウザでは JPEG エンコードだけネイティブ（`OffscreenCanvas.convertToBlob`）にする。ピクセルは resvg の出力のままなので見た目は変わらないが、出力バイト列が環境ごとに変わる。ADR-0005 の「描画は 1 系統」の範囲かどうかを ADR で判断してから行う。
