# ADR-0017: 画像のサイズ変更は、ベース画像を残したまま保存する画像の大きさ `canvas.output` として持つ

- ステータス: 提案中
- 日付: 2026-11-13
- 決定者: Shun（2026-11-13 に「キャプチャ後にサイズ変更したい」「幅×高さを数値で入れたい」と依頼。方式はスレッドの選択肢で「書き出しサイズだけ変える」を選択。この ADR を含む PR のマージで承認）
- 関連: FR-EDIT-24 / FR-CAP-10 / [注釈ドキュメントモデル](../03-design/document-model.md) / [ADR-0004](./0004-image-container-format.md) / [ADR-0005](./0005-rendering-pipeline.md) / [ADR-0007](./0007-pii-masking.md)

## 背景

利用ガイドに貼る画像の大きさを揃えたい（Retina で撮った 2 倍の画像を画面と同じ大きさにしたい、記事ごとに幅を揃えたい）という要望がある。いまは保存する画像がベース画像と同じ大きさにしかならない。

Harie の価値は「保存したあとも何度でも直せる」ことで、ベース画像は読み込んだバイト列のまま埋め込み、再エンコードしない（ADR-0004）。

## 選択肢

### A. 保存する画像の大きさ `canvas.output`（任意）を足し、描くときだけ拡大縮小する

- 長所: ベース画像・注釈の座標は変わらない。あとから何度でも変えられ、元の大きさに戻せる。画質を失わない。描画は SVG の `width` / `height` を変えるだけで、`viewBox` はそのまま（ADR-0005 の 1 系統のまま）。
- 短所: 縮小して保存してもベース画像は元の大きさのまま埋め込むので、ファイルは軽くならない。古い版は `output` を知らずに捨て、元の大きさで保存する。

### B. ベース画像そのものを指定の大きさに描き直して置き換え、注釈を `rebaseDocument` で合わせる

- 長所: ファイルが軽くなる。古い版でも同じ大きさで開ける。
- 短所: ベース画像を再エンコードする（ADR-0004 に反する）。縮小した画質は戻せず、「何度でも直せる」と合わない。

## 決定

A を採る（Shun が選択）。

- `canvas.output` は `{ width, height }`（1〜8192 の整数）。省略は表示範囲（`crop` があればその範囲、なければ画像全体）と同じ大きさ。表示範囲と同じ大きさを選んだときは記録しない。
- 縦横比が表示範囲と違えば、縦横それぞれの比率で伸び縮みさせて描く（SVG の `preserveAspectRatio="none"`）。エディタは既定で縦横比を保つ。
- 変更は操作 `setOutputSize`（`size: null` で元の大きさ）で行う。エディタの元に戻す・MCP の `harie_edit` も同じ操作を使う。
- 保存・コピーする画像（`renderer.render`）は `output` の大きさで描く。エディタの表示と、MCP が返す確認用の画像は、注釈の座標と見比べられるようベース画像の大きさで描く。
- ベース画像を差し替える（FR-EDIT-10）と、`output` も注釈と同じ縦横の比率で合わせる（同じ画面を撮り直したなら変わらない）。
- `canvas` を loose にし、今後 `canvas` に足す項目は、この版以降では知らなくても保存時に消さない。
- `schemaVersion` は上げない。古い版（ストア公開済みの Chrome 拡張、npm の @harie/mcp 0.7.0 まで）は `output` を捨てて元の大きさで保存するが、ファイルは開ける。

## 結果（影響）

- 良くなること: 保存する画像の大きさを、画質を失わずに何度でも変えられる。
- 受け入れるコスト: 縮小してもファイルは軽くならない。古い版で保存し直すと大きさの指定が消える。
- 後でやること: トリミング（FR-EDIT-09、`canvas.crop`）の UI を作るときは、`output` を表示範囲の大きさの基準と合わせる。
