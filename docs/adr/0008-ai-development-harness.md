# ADR-0008: AI 駆動開発のハーネス（CLAUDE.md / docs / ADR）

- ステータス: 承認
- 日付: 2026-10-07
- 決定者: Shun（2026-10-07 PR #1 のマージで承認）
- 関連: [ADR-0001](./0001-record-architecture-decisions.md) / [開発ルール](../05-development/development-rules.md) / [AI 開発ハーネス](../05-development/ai-harness.md)

## 背景

Harie は Claude Code などの AI エージェントが実装の大部分を担う前提で開発する。AI エージェントは会話ごとに記憶がリセットされるため、次の情報がリポジトリ内に、読む順序が明確な形で置かれている必要がある。

- プロダクトの目的と要件（何を作るか）
- 判断済みの事項とその理由（何を作らないか、なぜこの方式か）
- 開発の規約と検証方法（どうやって作り、どうやって正しいと確認するか）

## 選択肢

### A. CLAUDE.md を入口に、docs/ と ADR に詳細を置く（段階的開示）

- 長所: CLAUDE.md を短く保てる（毎回読み込まれるのでトークンを食わない）。詳細は必要なときだけ読む。人間も同じ文書を使う。
- 短所: 文書間のリンク切れ・陳腐化に注意が要る。

### B. CLAUDE.md にすべて書く

- 長所: 1 ファイルで完結。
- 短所: 肥大化して重要な指示が埋もれる。人間向け文書と二重管理になる。

### C. 文書を持たず、都度プロンプトで伝える

- 長所: 手間がない。
- 短所: 再現性がない。人やセッションによって品質がばらつく。

## 決定

**A を採用する。**

- `CLAUDE.md`（ルート）: 50〜150 行程度。プロダクト一行説明、ディレクトリ地図、必須コマンド、絶対に守るルール、詳細文書へのリンクのみ。
- `AGENTS.md`: 他の AI ツール向けに `CLAUDE.md` を参照させる。
- `docs/`: 要求・要件・調査・設計・計画・開発ルール。人間と AI が共有する正。
- `docs/adr/`: 判断の履歴。
- 要件 ID（`FR-*` / `NFR-*`）を PR・テスト名から参照し、要件 → 実装 → テストを追跡可能にする。
- 検証は `pnpm check` 1 コマンドに集約し、AI エージェントは PR 前に必ず実行する。
- 繰り返す作業手順は `.claude/skills/` や `.claude/commands/` にまとめる（コードが入ってから追加）。

## 結果（影響）

- 良くなること: どのセッションでも同じ前提から作業を始められる。判断の蒸し返しが減る。
- 受け入れるコスト: 仕様変更時に文書も更新する（PR テンプレートでチェック）。
- 再評価の条件: AI が文書を無視・誤読する事例が続いたら、CLAUDE.md の書き方やフックによる強制を見直す。
